SECTION 2: BUGS FOUND AND FIXED (during dry-run)
================================================================================

Bug 1 — exit code propagation (CRITICAL for CI)
  Location: src/main/main.ts, KOVIX_E2E_VERIFY and KOVIX_CHECK_KEY handlers
            (app.whenReady callback, ~line 1158 and ~line 1180).
  Symptom: When runEndToEndVerification() threw an error (or set
           process.exitCode = N internally), the outer try/catch set
           process.exitCode = 1 (or left it at the internal value) and called
           app.quit(). Electron's app.quit() can exit with 0 even when
           process.exitCode is non-zero. As a result, test/verify-end-to-end.ts
           saw child exit code 0, printed '✅ end-to-end verification
           complete', and exited 0 — silently reporting a FAILED run as
           SUCCESS. This is a serious CI correctness bug: any future
           regression that causes the e2e run to fail would be invisible.
  Fix: Replace app.quit() with app.exit(Number(process.exitCode) || 0) in
       both handlers. app.exit(code) is synchronous and honors the exit code.
       Applied to both KOVIX_CHECK_KEY and KOVIX_E2E_VERIFY handlers. The
       existing KOVIX_VERIFY (headless) and KOVIX_TEST_SETTINGS handlers
       were NOT touched (out of scope for this task), but they likely have
       the same bug and should be fixed in a follow-up.
  Commit: 0379b3c

Bug 2 — silent ollama fallback masked the 'no config' case
  Location: src/main/main.ts, runEndToEndVerification() (~line 1622).
  Symptom: When no provider is configured in the settings store AND no
           ANTHROPIC_API_KEY / OPENROUTER_API_KEY / NVIDIA_API_KEY env var
           is set, resolveProviderConfig() silently falls back to local
           ollama (source=env, no key). The e2e verify script's 'requiresKey'
           check then PASSED (ollama doesn't require a key), so the script
           proceeded to call ollama, which failed with a confusing
           'Ollama is not reachable or has no models installed' error —
           instead of the clean exit-2 'no provider config' message the
           task spec expects for the BLOCKED path. The script exited 0
           (due to Bug 1) on top of that, so the failure was doubly hidden.
  Fix: Detect the default local fallback (source=env + local provider +
       no key + no OLLAMA_BASE_URL) and exit 2 with an actionable message
       telling the user to configure a cloud provider via the UI. Users
       who explicitly want to test against a local Ollama instance can opt
       in via KOVIX_VERIFY_ALLOW_LOCAL=1 (plus OLLAMA_BASE_URL) so we know
       it's intentional, not the silent default.
  Commit: 0379b3c

After both fixes, 'npm run verify:e2e' with no key configured exits 2 with
a clear 'No real provider config available' message — exactly what the
task spec requires for the BLOCKED path.

SECTION 8: code review notes — verify-end-to-end.ts + runEndToEndVerification()
================================================================================

The task asked for a careful read of test/verify-end-to-end.ts and the
runEndToEndVerification() function in src/main/main.ts, noting any bugs,
missing edge cases, or assumptions that might break with a real key.

CONFIRMED BUGS (fixed in this branch):
  - Bug 1 (exit code propagation) — see SECTION 2. FIXED.
  - Bug 2 (silent ollama fallback) — see SECTION 2. FIXED.

POTENTIAL EDGE CASES (not fixed — noted for future, may or may not bite
with a real LLM):

  E1. Refinement rounds count check (line ~2047):
      The final verdict checks 'refineRounds >= 3 && refineRounds <= 5'.
      refineRounds is incremented AFTER each Q/A exchange, so if the LLM
      emits a spec on round N, refineRounds = N-1 at that point. With
      RefinementService configured for minTurns=3, maxTurns=5, the LLM is
      forced to ask at least 3 questions before emit_spec is allowed, so
      the spec should come on round 4 (refineRounds=3) at the earliest.
      This SHOULD pass. But if a real LLM finds a way to emit early (the
      service has correction logic but it's not bulletproof) or if the
      hard cap of 8 iterations in the verify script is hit before
      refinement converges, this check could fail. Worth watching.

  E2. 'complete' event check (line ~2054):
      The verdict requires completeReceived=true. The 'complete' event is
      only emitted by the agent loop's run() when it finishes normally. If
      the agent errors out (e.g. LLM returns an unrecoverable error mid-
      milestone), no 'complete' is emitted and this check fails — even if
      files were successfully written before the error. This is probably
      the right behavior (we want a clean complete), but it means a single
      LLM hiccup near the end of execution fails the whole run.

  E3. Verification runs npm test/build/typecheck in buildDir (line ~1948):
      The runVerification() function runs 'npm test' (or build/typecheck)
      in the buildDir. If the agent-generated project has a package.json
      with a test script but no node_modules installed, 'npm test' will
      fail because dependencies aren't installed. The agent would need to
      either generate a project with no dependencies, or the verify script
      would need to run 'npm install' first. This is a real concern for
      the 'npm test' path; the 'npm run build'/'typecheck' paths may work
      if the generated project uses plain tsc with no deps. Not a bug per
      se, but a likely failure mode with a real LLM.

  E4. 10-minute hard cap (line ~1880, TIMEOUT_MS = 10*60*1000):
      The execution stage has a 10-minute hard cap. With a real LLM, each
      call can take 10-30s, and a multi-milestone plan might make 20-50+
      LLM calls. 10 minutes may be tight for complex ideas. If the timeout
      fires, execAborted=true and the run fails. Worth lengthening for
      real-key runs, or making it configurable via an env var.

  E5. Approval callback always returns true (line ~1719):
      The approveWrite callback always returns true (auto-approves every
      staged write). This is correct for headless verification (we want
      the run to proceed), but it means the 'approval gate' isn't actually
      gating anything — it's just verifying that staging blocks the write
      before approval (which is the real test). The verdict check
      'Approval callback fired' confirms staging invoked the callback,
      which is the right thing to verify. No bug, just worth understanding.

  E6. autoResume always resumes (line ~1757):
      The autoResume callback always returns 'resume' after 1 second. This
      is correct for headless verification (we can't have a human decide
      at each pause). With pauseMode='auto' (the default), there are no
      pauses anyway, so autoResume is never called. With 'every' or
      'major' or 'custom', autoResume fires at each pause point and
      auto-resumes. This means pauseMode doesn't really test the pause
      UI — it just tests that pause events are emitted and auto-resumed.
      Acceptable for headless verify.

  E7. Settings file path assumption (settingsStore.ts line 81):
      settingsFilePath() uses app.getPath('userData'). On Linux this is
      ~/.config/<appName>. The appName comes from package.json "name"
      ("kovix-standalone"). If the app name ever changes, old settings
      files become orphaned. Not a bug, just a coupling to note.

OVERALL ASSESSMENT:
  The verify script is well-structured and the real-key path (which we
  couldn't exercise here) should work end-to-end once a key is present.
  The two bugs fixed in this branch were both in the FAILURE path (what
  happens when no key is present), not the success path. The success path
  logic (refinement → spec → plan → execute → verify) looks sound. The
  edge cases above are things to watch when the real run happens, not
  blockers.
